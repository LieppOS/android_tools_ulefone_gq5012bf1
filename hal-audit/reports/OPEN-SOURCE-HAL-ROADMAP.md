# Open-source HAL roadmap — GQ5012BF1

## Evidence and decision rules

This is the retained C51 **OS/HAL integration** roadmap, with only the vibrator row updated through C51C. Other subsystem/vendor-root observations are historical C51 inputs, not a new audit of C54 work. One independently authored vibrator service spans existing MediaTek/Ulefone owners; it remains unselected, disabled and not Soong-linked. Existing clients/helpers are not HAL servers.

**C51C vibrator source coverage:** frozen AIDL V2/default, INDEPENDENT Apache-2.0 HAL, now strictly requiring driver-owned kernel timeout ABI1. The GPL-2.0 kernel driver/private policy were implemented and built as a real module with unchanged C50 config/core exports, then synchronized to the existing Ulefone provenance mirror. HAL34/34 normal+ASan/UBSan,22/22 TSan; shared kernel policy12/12 each mode+4 static guards;96/96 Python checks;6/6 genuine ARM64 source objects compile. No full Android link, kernel runtime or hardware proof. See readiness, SAFETY.md and the existing research handoff for scope and closed deployment gates.

For every inventory record, apply its subsystem row below; multiple radio slots/instances share a workstream, **not** a functionality verdict. The vendor-family section covers the remaining declared interfaces. Exact declarations, instances, versions, filenames, source references and hashes remain in `HAL-INVENTORY.json`/CSV; this document does not replace either the specialized inventory or the canonical hardware inventory.

- **Retained artifact reference** means an entry in the proprietary extraction list, not an inspected binary, proprietary-license finding, or proof that upstream source does not exist.
- **EXTRACT_ONLY / product package** means an intended source replacement or build dependency, not proof source was imported or correctly adapted.
- **Upstream candidate** is an implementation/reference family to evaluate. Except for the explicitly pinned C51 interface/source checks, no candidate below is validated for the device or target platform; no hardware verification is claimed.
- Exact proprietary/kernel ABI matching is generally unresolved. Listed boundaries are architectural questions, not claims that a particular live node or ioctl was verified.
- Do not invent a mandatory HAL for every feature. Requirements depend on actual hardware exposure, shipping FCM, framework matrices and product configuration.

**No reverse-engineering campaign is recommended here.** First locate and verify existing source and vendor-supported integration, including suitable chipset/OEM implementations and their licenses. This audit has not established their global unavailability. Any remaining new implementation proposal requires a separate owner-approved decision after that search and platform validation.

## Practical order

1. **Metadata completeness:** obtain already-existing sanitized fragment/rc/config bodies and exact framework matrices. Resolve literal product/source selection, 48 override overlaps and the single AEE coexistence review before proposing replacements.
2. **Small, bounded adaptations:** evaluate existing source for lights, vibrator, health, USB and auxiliary input clients after confirming exact ABI/configuration. Keep unverified capabilities unadvertised.
3. **Glue versus backend:** resolve Wi-Fi, sensors multihal, audio and camera glue separately from MTK middleware/firmware. Importing a generic adapter does not open the backend.
4. **Security/graphics/modem boundaries:** require source provenance, version/ABI validation and explicit safety planning; do not replace secure-world or certified services with examples.
5. **Per-subsystem evidence:** only promote to HARDWARE_VERIFIED after explicit operation tests on a hashed, owner-approved image set. C46 boot completion and `init.svc=running` are insufficient.
